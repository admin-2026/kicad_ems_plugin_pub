Running the solver in a container

A simulation can run inside a Docker container instead of directly on your machine. The solver then sees one folder — the one this board's simulation writes into — and no network at all.

What Docker is

Docker runs a program inside a container: a packaged filesystem with its own copy of everything the program needs, and only the access to your machine that it is explicitly given. Nothing is installed into your system to run one, and nothing is left behind when it stops. The container here is built from a recipe this plugin ships, on your machine, and never leaves it.

Docker itself is separate software and you install it once, from https://www.docker.com/ — Docker Desktop on macOS and Windows, Docker Engine on Linux. It is free for personal use and for small businesses; the site states the current terms.

Why you might want it

The image is a workbench: KiCad, this plugin, its command line and the solver, together in one place. Which makes the interesting use of it possible — putting an AI agent in there with them and letting it do the whole job inside. It reads the board, writes the settings, starts a run, reads the results and tries the next candidate, and at no point does it touch anything of yours except the one directory you mounted.

An agent designing something is confidently wrong from time to time, and it is wrong while nobody is watching. Inside the container there is not much for that to cost: one directory is visible and writable, and your home directory, your other projects and the rest of the machine are simply not there to be reached. A mistake stops at the edge of the project instead of being found afterwards by reading what it did. The network is the one thing to decide for yourself — a solve this window starts has none at all, while an agent that has to reach its model does, so a container you start for one is as connected as you make it and no more.

Ticking the box uses the same boundary one solve at a time: every run this window starts then goes through the container. It costs a one-off build (minutes, and a few hundred megabytes) and a little start-up time per run. The simulation runs at the same speed and computes exactly the same numbers.

On macOS it is not optional. No macOS build of the solver ships, so on a Mac every simulation runs in the container and the tick on the About page is shown ticked and greyed. Everything else — the window, the board, the markers, the results — runs on your Mac as usual.

Setting it up

  1. Install Docker. Docker Desktop on macOS and Windows, Docker Engine on Linux. The About page's Docker box says which of these is missing, if any.
  2. Build the image with the Build image button. It installs KiCad inside the image, so it takes a few minutes the first time; the log at the foot of the About page prints what the engine is doing while it does it. The same button appears on the banner under the form when a run is stopped because no image has been built yet, and starts the same build from there. Once an image exists that button is named Rebuild image — it is one button, named for what pressing it will do.
  3. Tick the box (already ticked on macOS). From then on, runs started from this window and from the command line go through the container.

Rebuild it after a plugin update

The image carries this plugin's own code, so an image built by an older release is not the right one for a newer install. The box reports that as stale, and Rebuild image is the answer. Rebuilding is also what to do if the KiCad inside the image is older than the KiCad you are running: an older KiCad cannot open a board a newer one saved, and the box reports that too.

What is inside, and what it can see

The image holds KiCad, this plugin, its command line and the solver. During a run the container is given exactly two things: the board's simulation folder, which it may write to, and the plugin's solver binaries, which it may only read. It has no network, no access to your home directory, and it is removed when the run ends.

Because the plugin and its command line are in there too, the image is also somewhere to work: mount a project folder and you have the whole command line, with KiCad's Python, inside the container. The two licence files — the plugin's and the solver's — are copied in beside the code they cover, at /opt/plugin, so the terms can be read without a checkout anywhere near.

Two commands you can copy

Both are typed in your own shell, in the folder your board is in. That folder becomes /work inside the container and is the only thing of yours it can see, so a board named there is /work/board.kicad_pcb.

A shell inside it, to look round — KiCad, this plugin and the solver are all in here:

docker run --rm -it -v "$PWD:/work" antenna-workbench:latest bash

The command line inside it, driven from outside — the same verbs the Command line guide describes, running on the container's KiCad rather than yours:

docker run --rm -v "$PWD:/work" antenna-workbench:latest antenna-agent preflight --board /work/board.kicad_pcb

docker run --rm -v "$PWD:/work" antenna-workbench:latest antenna-agent run start --board /work/board.kicad_pcb

Naming antenna-agent is optional — anything that is not a program is handed to it anyway, so versions alone works — and --rm means nothing is left behind when the command finishes. Add --network none to cut the container off from the network as a solve started by this window is.

The recipe, if you want to change it

The image is built from a Dockerfile that ships inside this plugin, at

<the installed plugin>/emkit/sim/container/Dockerfile

Where the installed plugin is depends on where KiCad keeps its plugins, so the window prints the whole path rather than describing it: it is the first line of the Image build log at the foot of the About page, ready to be selected and copied. The command line's docker status prints the same path.

It is a plain text file with a comment above every step saying why that step is there. Edit it — a package your board needs, a different base, an extra tool to work with inside the container — and press Rebuild image; the button builds whatever the file now says. Nothing else has to be told.

No agent is in the image, and that is on purpose: which one, on what terms and billed to whose account is not ours to decide for you. The file has a commented block, just before the last few lines, saying where to put yours and what a container running one needs that a solve does not — a network, since a solve is started with no network at all, and its API key, which belongs on the docker run that starts it and never in the recipe. A key written into the file is in the image, and stays there.

To add a tool, put one more step after the block that installs KiCad — this one adds gerbv, a gerber viewer, so that what a run plotted can be looked at inside the container:

RUN apt-get update && apt-get install -y --no-install-recommends gerbv && rm -rf /var/lib/apt/lists/*

Then Rebuild image. The three parts of that line are worth keeping in the habit: update because the package lists are not in the image, --no-install-recommends because the recommendations of a desktop package are a desktop, and the rm because the lists would otherwise stay in the layer for good.

Two things to leave alone unless you mean them: the KiCad in the image must not be older than the one you run (it could not read your boards), and the COPY lines are what put this plugin, the solver and their licences inside. An upgrade of the plugin replaces this file, so keep a copy of any edit you want to survive one.

Stop and Snapshot still work. They travel through a file in the run folder rather than through the operating system, so a run inside a container is as interruptible as one outside it — and closing this window still ends the run.

Things worth knowing

  • Installed, but reported missing. A window opened from the Dock or the Start menu does not inherit your terminal's PATH, so this plugin looks for Docker where the installers put it as well as on that path. If you installed it somewhere of your own, link it into /usr/local/bin and the window will find it.
  • A build that stops on a credential helper. docker-credential-desktop: executable file not found is the same thing one level down: Docker runs small helper programs of its own and looks for them on the path it was given. They live beside the client, which is where this plugin points it, so a helper you keep elsewhere wants the same link into /usr/local/bin.
  • File sharing on macOS and Windows. Docker Desktop only shares the folders you have listed in its settings. A project outside those cannot be mounted, and the run says so.
  • Memory. Docker Desktop runs a virtual machine with a memory limit of its own, and the solver sizes its mesh against what it can see. If a run that fits natively refuses inside the container, raise the VM's memory in Docker Desktop's settings.
