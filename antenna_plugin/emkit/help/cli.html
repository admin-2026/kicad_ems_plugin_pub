From a command line

Everything this plugin does — checking a board, running a simulation, reading what it came to — can also be done by typing a command instead of pressing a button. This page is what to type, and what comes back.

What it is for

The window and the command line are two ways into the same work: the same board, the same simulation/ folder beside it, the same answers. The window reads its boxes when you press Run; the command line reads what the window saved. So neither is a lesser copy of the other — but typing is what you want when the one doing the work is not a person sitting here:

  • Doing it again. The same check on ten boards, or on one board after every edit, without ten trips through this window.
  • A script, or a CI job. Every command can answer in JSON as readily as in sentences, so something else can read it.
  • An AI agent. It has no hands for a dialog box. Given one command it can check a board, start a simulation, watch it and read the result.
Handing this to an agent? Give it one command: antenna-agent guide. That prints the whole briefing — what this plugin does, the order the commands go in, what a run costs, which files beside your board are safe to edit, and what this plugin can build. It needs no board and takes seconds, and it is what the rest of this page says, written for something with no eyes on this window.

Start here: the shortcut

On the About page — the one that opened this guide — find the Command line box and tick Install the shortcut. The box then shows you a command; open a new terminal and type it:

antenna-agent versions

If it answers with a table of version numbers, everything below this line works and you can skip to The commands.

Why a new terminal? A terminal that is already open keeps the settings it started with, and the tick has just changed one of them. Ticking the box writes a small script — with the right Python and this install's path already filled in — and adds the folder holding it to your own PATH, which is the list of places your terminal looks for a command. Only your account's, never the machine's, and nothing that asks for a password. Unticking removes both, exactly.

Which Python

You should not have to name one, and you should not install one for this. The shortcut has KiCad's own Python written into it — the interpreter this window is running under, recorded the moment it opened, which is the one moment the answer is known for certain.

That matters because reading a board needs pcbnew, the module KiCad's Python has and no other Python does. A virtualenv, a pyenv shim or Windows' Microsoft Store python.exe will all fail to find it, however KiCad was installed — so if you ever go looking for an interpreter yourself, it is one of these and nothing else:

SystemKiCad's interpreter
Linux/usr/bin/python3 — pcbnew ships inside the kicad package; there is no python3-pcbnew to install
WindowsC:\Program Files\KiCad\<version>\bin\python.exe — not on PATH by default
macOSKiCad.app/Contents/Frameworks/Python.framework/Versions/Current/bin/python3

The commands

Each one is a word, or two: preflight, run start, results show. Every one of them answers on standard output and answers alone — nothing here opens a window, and nothing waits for you to click.

VerbWhat it answers
guideThe whole briefing in one page — written for an agent, readable by anyone. Needs no board.
settings initWrites a starter settings file for a board that has none — the same form this window saves, with the frequency left for you to fill in.
preflightWhat would stop a run: the same checks as the banner at the top of this window.
run startStarts a solver and answers with a job id, immediately. See below.
run statusWhich phase, how long, and whether it is still going.
run logThe solver's output. It is a flood, so --since resumes from the offset the last one returned.
run sampleWrite a report from the record so far and keep stepping.
run stopEnd early. See the note below — this is not throw-away.
results showWhat the last run came to: the numbers, the verdict, and the address of the page that draws them.
versionsThe same table the About page shows — the things to quote when something misbehaves.
docker statusWhether a solve can run inside a container on this machine — and if it cannot, what to do about it.
docker buildBuild that container's image. Minutes: it installs KiCad.
docker rebuildDelete the image and build it again — what a plugin upgrade needs, since the plugin's own code is inside it.
docker onRun solves in a container from now on, on this machine.
docker offRun them natively again. Refused where no native solver ships.

Every command but guide, versions and docker takes --board <path.kicad_pcb> — it reads the file, not whatever this window has open — and --help on any of them is the full list of its options.

Running the solver in a container

A run is otherwise a native process with your own rights, reading and writing anywhere you can. That is fine when you started it and are watching it. When something else is driving — a script, an agent — a solver that can see one mounted directory and no network is a better default, and it costs a flag:

antenna-agent run start --board b.kicad_pcb --docker

The image holds KiCad, this plugin, its command line and the solver, so it is also somewhere to work: mount a project directory at /work and every command on this page is there, with the shortcut already installed. docker status names the image; the project's docs/docker.md has the commands for opening a shell in one.

Build it once with docker build, and again after every plugin upgrade — the plugin's own code is copied into the image, so an upgraded install asks for an image tag that does not exist yet. docker status says which of those is true right now. On macOS this is not optional: no macOS build of the solver ships, so docker off is refused there and every run goes through the container.

Add --json to any command and the answer comes back as JSON instead of sentences. The flag goes before the command, and a usage error comes back as JSON too, so a program reading the output never has to also watch for an English sentence on the error stream.

A run takes minutes, so it detaches

A solve is minutes, not seconds, so run start does not wait: it hands back a job id — the timestamp naming the folder that run is writing into — and leaves the solver going. Follow it with run status and run log, sample it or stop it at any point, and read it with results show when it ends.

Stop still writes a report. Both stop and sample are requests the solver picks up on its next step, and stopping writes the report for the record so far rather than throwing it away — the same thing this window's Stop button does. Because the channel is a file and not a signal, both reach a run whoever started it: this window, another shell, or a session that has since closed.

What is refused rather than warned about is a second run on a board that already has one going — they would write one config, overwrite each other's dumps and share one stop request. The refusal names the job already running and how to end it. A run alongside a different board's run is fine.

One run, start to finish

Below, board.kicad_pcb stands for the path to your board. One thing to know before you start: a run is built from the board's simulation/settings.yaml — the same form this window saves whenever it closes or starts a run. Edit a copy of that file and point the run at it (--settings my.yaml): this window rewrites its own. A board that has never had this window open on it has no such file, and antenna-agent settings init --board board.kicad_pcb writes one.

  1. antenna-agent preflight --board board.kicad_pcb — is there anything wrong with the board itself? Costs milliseconds, and is worth doing first: everything it reports would stop the run anyway.
  2. antenna-agent run start --board board.kicad_pcb --settings my.yaml — runs a copy of the settings file that you edited, instead of the one this window keeps rewriting. Leave the flag off to run the board's own.
  3. antenna-agent run start --board board.kicad_pcb --grid-only — the mesh alone, which is the short part of a run: it stops once the lattice is built, and everything the solver has to say about the board — the cell it settled on and every ground warning — is printed before that point. Read it with run log; it writes the grid and no report, so there is nothing new for results show. The mesh it previews is the one the solve would use.
  4. antenna-agent run start --board board.kicad_pcb — answers a job id straight away and leaves the solver going. What the results are judged against is the settings file's, not a flag's: the run is scored against the design target the form names — the same pick this window's target picker writes into it — so editing that one field is how a run is aimed. A flow with nothing to judge against reports its numbers unjudged and says so.
  5. antenna-agent run status --board board.kicad_pcb — which phase, how long, and whether it is still going. This is the one to poll.
  6. antenna-agent run log --board board.kicad_pcb --since 240 — the solver's output from line 240 on. Every log answers with the offset to pass next time, so a poller never re-reads what it has seen.
  7. antenna-agent results show --board board.kicad_pcb — the numbers, the verdict against the form's target, and the address of the page that draws them.

Any of them in JSON, with the flag before the command: antenna-agent --json run status --board board.kicad_pcb.

The rest, in one line each

CommandWhy
antenna-agent run sample --board board.kicad_pcb Write a report from the record so far without ending the run — a look at where it is going, mid-flight.
antenna-agent run stop --board board.kicad_pcb End early, keeping the report. Reaches a run this window started as readily as one a shell did.
antenna-agent run status --board board.kicad_pcb --job 20260902-181500 An older run rather than the newest. A job id is the stamp of the run folder it wrote; --board is still what says which board's runs to look through.
antenna-agent results show --board board.kicad_pcb --job 20260902-181500 The numbers of that same older run. Every command takes the one id — there is no path to a dump to look up, and a run this window started is readable by its stamp too.
antenna-agent settings init --board board.kicad_pcb --out my.yaml A starter form of your own, somewhere this window will not overwrite it. Every key it can hold, and what each picked value means, is in antenna-agent guide.
antenna-agent run start --help The full options of any command. There is nothing this page has that --help does not.

--help works at every level. Add it to as much of a command as you have typed and it answers about that much: antenna-agent --help lists the commands, antenna-agent run --help the things run does and the options they take, antenna-agent run start --help the same for that one. So there is nothing to memorise from this page — every command tells you the rest of itself.

What it cannot do

  • It will not fill the form in for you. settings init writes the toggles, the picks and a material row per layer, and leaves blank everything the plugin has no business choosing — there is no default frequency for a board. A run refuses a blank one by name rather than inventing a number.
  • It cannot see the board you have open. It loads the file from a path and reads it as it was last saved. An unsaved edit is invisible to it; zone fills are read as stored, and nothing refills them.
  • It does not draw on the board. Placing markers and copper is this window's work.
No silent defaults, here least of all. A missing input fails and names itself rather than being filled in with a plausible number. That rule matters more at a command line than at a form: a caller leaving a field out is easier to do, and harder to notice, than a person clearing a box.
